# UI Match — Real Service Icons + View-Appropriate Titlebar Chrome

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show real service logos everywhere a service is named (rail, manager, titlebar), and stop the titlebar offering service-only controls in the manager view.

**Architecture:** Purely presentational. Every icon comes from the `loft://icon/<id>` protocol that `src/main/index.ts` already registers — no new assets, no new state, no model changes. The one piece of plumbing is a single IPC channel, `titlebar:set-context` (`string | null`), because showing the service icon and showing the service-only controls answer the same question: is this titlebar showing a service, or the manager?

**Tech Stack:** TypeScript, Electron 43, Svelte 5 (runes), Vite. No new dependencies.

## Global Constraints

- **`src/renderer/rail/rail.ts` MUST stay import-free.** It is tsc-`commonjs` loaded as `<script type="module">`; a value `import` emits `require`/`__esModule` and throws at load, silently killing the whole rail. Only inline `type X = import('...').Y` type queries are allowed. Verify with `grep -n "^import\|require(" src/renderer/rail/rail.ts` — it must print nothing.
- **`rail.ts` and `titlebar.ts` share one global TypeScript scope** (neither has a top-level import/export), so a top-level `const` in one collides with the same name in the other (TS2451). Do not reuse identifiers across those two files.
- **Icons come only from `loft://icon/<id>`.** No new image assets, no bundling, no icon picker.
- **Icon failure must never blank a control.** In the rail, fall back to the initials placeholder; in the manager and titlebar, hide the image (the name is rendered beside it).
- **No changes to `managerModel.ts`, `railModel.ts`, or any main-process model.** `managerNav` already returns each service's `id`, which is all an icon URL needs.
- Build with `npm run build`; type-check the hub with `npm run check`; tests are `npm test`.

**Testing note for every task:** this slice has no unit-test seam — `rail.ts` is import-free by constraint, the titlebar preload calls `contextBridge` at import time with no injectable factory, and there is no Svelte component test infrastructure. Tasks are therefore verified by `npm run build`, `npm run check`, and `npm test` staying green (nothing here should change behaviour those tests cover). Do **not** add test scaffolding to make these testable — that is explicitly out of scope.

Append to the end of `src/renderer/titlebar/titlebar.ts`:

```ts
// One signal drives both the icon and the service-only controls, because they answer the
// same question: is this titlebar showing a service, or the manager? A null id is the
// manager view, where reload and the zoom buttons would act on a web view that is not
// there. Close stays in every view, and ⇤ keeps its own set-attachable logic — "is this a
// detached window" is a different question from "is this showing a service".
const iconEl = document.getElementById('icon') as HTMLImageElement;
const serviceOnly = ['reload', 'zoom-out', 'zoom-in']
  .map((el) => document.getElementById(el) as HTMLButtonElement);

iconEl.addEventListener('error', () => { iconEl.hidden = true; });

window.loft.onSetContext((id) => {
  if (id !== null) iconEl.src = `loft://icon/${id}`;
  iconEl.hidden = id === null;
  for (const el of serviceOnly) el.hidden = id === null;
});
```

    if (!active) {

The spec's non-goals are respected — no model changes, no new assets, no layout revert, no tray/notification icon changes.

**Placeholders.** None — every step names an exact file, shows the exact code to replace and the exact replacement, and every command states its expected output.

**Type consistency.** `titlebar:set-context` carries `string | null` identically in the preload (T4 S1), the window type (T4 S2), the renderer (T4 S5) and both senders (T4 S6, S7). The CSS class `ico` is used consistently in Task 2 for both manager surfaces; the rail's icon class is `icon`, scoped as `.item .icon`, and does not collide with it. `ServiceDetail` uses its existing `id` prop rather than a new one.

**Deliberate deviation from strict TDD**, stated once in the Global Constraints and not repeated per task: this slice has no unit-test seam (import-free renderer, no preload factory, no Svelte component test infrastructure), so tasks are verified by build + svelte-check + the existing suite staying green, then by the Task 5 smoke test. Adding test scaffolding is explicitly out of scope. No task's logic was pushed into an untestable place that could have lived in a tested one — there is no decision logic here beyond `id !== null`.
