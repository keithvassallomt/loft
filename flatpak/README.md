# Loft Flatpak (from-source, FriendlyHub + standalone bundle)

This directory holds the pieces of the **from-source** Flatpak build for Loft's
Electron app. Unlike the deb/rpm/AppImage artifacts (produced by
`electron-builder`), the Flatpak is a hand-written `flatpak-builder` manifest
(`../chat.loft.Loft.yml`, at the repo root) that compiles the app **from source
inside the sandbox** on the Electron base app with zypak, using Node offline
sources so the build needs no network access of its own.

This is the format shipped on [FriendlyHub](https://friendlyhub.org) and as a
standalone `.flatpak` bundle attached to GitHub Releases. It is **not** on
Flathub (Loft is a plain Electron app here and doesn't need a sandbox escape, so
this manifest is Flathub-clean, but distribution is via FriendlyHub to match the
rest of the project).

## Files

| File | Purpose |
|------|---------|
| `../chat.loft.Loft.yml` | The `flatpak-builder` manifest, at the repo root. **This is the file uploaded to FriendlyHub verbatim**, so its app source is `type: git` pinned to the release tag. |
| `../generated-sources.json` | Offline Node sources (npm tarballs + Electron prebuilt binaries + node headers), generated by `flatpak-node-generator`. Committed; regenerate when `package-lock.json` changes. At the repo root because the manifest must reference it by **bare filename** (see FriendlyHub upload below). |
| `../chat.loft.Loft.dev.yml` | Generated (`npm run flatpak:dev`), gitignored: the same manifest with the git source swapped for the working tree. Use this for local iteration. |
| `../scripts/flatpakDevManifest.mjs` | The generator. Rewrites only the marker-delimited app-source block, so the dev manifest cannot drift from the submitted one. |
| `loft-launcher.sh` | zypak launcher installed as `/app/bin/loft` (the app's `command`). |
| `README.md` | This file. |

## Toolchain / runtime versions (verified live)

Verified against `flatpak remote-ls flathub` and
`electron/node_modules/electron/package.json` on 2026-07-14:

| Component | Choice | Notes |
|-----------|--------|-------|
| Runtime | `org.freedesktop.Platform//24.08` | freedesktop-sdk-24.08.x |
| SDK | `org.freedesktop.Sdk//24.08` | |
| Base app | `org.electronjs.Electron2.BaseApp//24.08` | Provides `zypak-wrapper` + Chromium's shared libs; must match the runtime branch. |
| Node SDK extension | `org.freedesktop.Sdk.Extension.node22//24.08` | Build-time only (tsc/esbuild/vite). node22 matches the host toolchain (Node 22, npm 10) that produced the lockfile. |
| Electron (app) | `43.1.0` | Resolved from `electron/node_modules/electron/package.json`. The app **bundles its own** Electron binary (from `generated-sources.json`); the base app only supplies zypak + libraries. |

**Why 24.08 (and not 25.08).** Both `24.08` and `25.08` form a mutually
consistent set on Flathub today (runtime + sdk + `Electron2.BaseApp` +
`Sdk.Extension.node22` all exist on both branches). We chose `24.08`: it is the
more mature freedesktop branch (higher patch level) and the current well-trodden
target for Electron 43 apps on Flathub, which lowers the risk of a runtime
library-version surprise. Bump all four together if/when moving to `25.08`.

### Installing the runtimes locally

```bash
flatpak install -y --user flathub \
  org.freedesktop.Platform//24.08 \
  org.freedesktop.Sdk//24.08 \
  org.electronjs.Electron2.BaseApp//24.08 \
  org.freedesktop.Sdk.Extension.node22//24.08
```

## Regenerating the Node offline sources

**Use the canonical `flatpak-node-generator` from the flatpak-builder-tools
repo — NOT the PyPI package.** The PyPI `flatpak-node-generator` (0.1.1) is a
stale fork that silently under-generates for `lockfileVersion: 3` lockfiles: on
this project it captured only 121 of 538 unique package tarballs (missing
`electron`, `svelte`, `vite`, `esbuild`'s per-arch binaries, `dbus-next`,
`typescript`, …) and produced **no** Electron binary sources, which would make
the offline `npm ci` fail. The canonical build handles all of it.

```bash
# One-time: install the canonical generator
pipx uninstall flatpak-node-generator 2>/dev/null || true
pipx install "git+https://github.com/flatpak/flatpak-builder-tools#subdirectory=node"

# Regenerate (run from electron/)
cd electron
flatpak-node-generator npm package-lock.json \
  -o ../flatpak/generated-sources.json \
  --electron-node-headers
```

This produces ~1100 sources: the full npm `_cacache` (every lockfile tarball,
for **all** arches thanks to `lockfileVersion 3` listing every optional per-arch
package), the Electron prebuilt binary zips for `x64`/`arm64`/`armv7l`, the
matching `SHASUMS256.txt`, the Electron node headers, and small setup scripts
that pre-seed the caches. Because the arm64 tarballs are captured too, the same
`generated-sources.json` builds on FriendlyHub for both **x86_64 and aarch64**.

### How the offline Electron binary works

The finicky part of an offline Electron build is getting the prebuilt
`electron-v43.1.0-linux-<arch>.zip` (~220 MB, normally fetched from GitHub) in
place without network. We do **not** need `ELECTRON_SKIP_BINARY_DOWNLOAD` or any
manual zip sourcing — but there are two Electron-43-specific gotchas the manifest
handles explicitly:

**1. Electron 43 has no `postinstall`.** Older Electron packages ran
`node install.js` from a `postinstall` script, so `npm ci` extracted the binary.
Electron 43 removed that: its `node_modules/electron/index.js` downloads the
binary **lazily on the first `require('electron')`** instead. Nothing in
`npm run build` (tsc + esbuild + vite, all with `electron` marked `--external`)
ever requires electron, so `npm ci` alone leaves `node_modules/electron/dist/`
**empty** and the launcher would fail with "does not look like a valid Chromium
binary". The manifest therefore runs the installer explicitly as its own build
step:

```yaml
- cd electron && node node_modules/electron/install.js
```

`install.js` calls `@electron/get`'s `downloadArtifact`, which resolves its cache
root from `$XDG_CACHE_HOME/electron`. The canonical generator pre-builds that
`@electron/get` cache under `flatpak-node/cache/electron/` in **both** the
sha256-keyed layout (`@electron/get` v5 computes
`sha256("https://github.com/electron/electron/releases/download/v43.1.0")` =
`a791fa12…`) and the URL-sanitised layout (older `@electron/get`), so the lookup
hits regardless of the exact `@electron/get` version. With
`XDG_CACHE_HOME=…/flatpak-node/cache` set, `install.js` finds the cached zip,
verifies it against the bundled `checksums.json`, and unpacks it into
`node_modules/electron/dist/` (writing `path.txt`) — all offline.

**2. The launcher clears `ELECTRON_RUN_AS_NODE`.** If that variable is set in the
environment (Flatpak forwards much of the host env into the sandbox, and some dev
shells export it), Electron's main process runs as plain Node and
`require('electron')` returns the binary path string instead of the API object —
so `app`/`BrowserWindow`/… are `undefined` and the app crashes immediately
(`Cannot read properties of undefined (reading 'setName')`). `loft-launcher.sh`
`unset`s it before `exec zypak-wrapper …`; zypak re-sets it itself for the
sandbox-helper child processes it spawns, so clearing it only affects the browser
process. This mirrors the app's own `env -u ELECTRON_RUN_AS_NODE electron .` dev
scripts.

### Cache layout / manifest env

`flatpak-node-generator` lays two caches under the module build root
(`/run/build/loft`):

- `flatpak-node/npm-cache/_cacache` — npm's content-addressed cache → the
  manifest sets `npm_config_cache=/run/build/loft/flatpak-node/npm-cache`.
- `flatpak-node/cache` — XDG cache used by Electron, node-gyp and esbuild → the
  manifest sets `XDG_CACHE_HOME=/run/build/loft/flatpak-node/cache`.

Combined with `npm_config_offline=true`, `npm ci` installs entirely from cache.

## Build layout decisions

- **Manifest at repo root**, alongside `generated-sources.json`. Companion source
  files land *flat* next to the manifest in the FriendlyHub build repo, so the
  manifest must reference them by bare filename — which only resolves locally if
  the file sits next to the manifest too. `loft-launcher.sh` stays under
  `flatpak/` because it is read from the **checked-out tree** by a build command,
  not fetched as a source.
- **Git source, not `type: dir`.** See the FriendlyHub upload section below: a
  `type: dir` source is unbuildable on FriendlyHub. The dev manifest's `skip`
  list (`.git`, `build-dir`, `.flatpak-repo`, `target`, `node_modules`, `dist`,
  `dist-electron`) forces a clean offline install and keeps the copied tree
  small; a git clone is already clean, so the submitted manifest needs none.
- **App tree = `/app/main`.** `dist/`, `package.json`, and `node_modules` are
  copied there; `package.json`'s `main` points at `dist/main/index.js`, and the
  Electron binary lives in `node_modules/electron/dist/electron`. The launcher
  execs it under `zypak-wrapper`.

## Building locally

The committed manifest builds the **pushed release tag**, so it will not pick up
working-tree changes. Generate the dev manifest first:

```bash
# From the repo root
npm run flatpak:dev                    # writes chat.loft.Loft.dev.yml (gitignored)
flatpak-builder --force-clean --user --install --repo=.flatpak-repo \
  build-dir chat.loft.Loft.dev.yml

# Smoke-run (no display in CI: exit 124 from `timeout` means it stayed up)
flatpak run chat.loft.Loft            # opens the hub window
```

## Standalone `.flatpak` bundle (GitHub Releases artifact)

```bash
flatpak build-bundle .flatpak-repo Loft-1.0.0.flatpak chat.loft.Loft
```

Install with `flatpak install --user Loft-1.0.0.flatpak`.

## FriendlyHub upload

FriendlyHub builds the manifest itself for both architectures. Upload, **both from
the repo root**:

1. `chat.loft.Loft.yml` (the manifest), and
2. `generated-sources.json` (the offline Node sources it references).

FriendlyHub builds **x86_64** and **aarch64** from the same inputs (the offline
sources contain every arch's tarballs and Electron binary).

### The submission contract (this is what broke the 1.0.0 build)

FriendlyHub copies the uploaded files into `friendlyhub/chat.loft.Loft` and runs
`flatpak-builder` **there** — in a directory holding only the manifest, its
companion files, and the metainfo it injects. There is no checkout of this repo.
Two rules follow, both stated in
[friendlyhub/submissions](https://github.com/friendlyhub/submissions):

- **"Reference your app's source code using `type: git` with a URL pointing to
  your upstream repository (not `type: dir`)."** A `type: dir, path: .` source
  resolves to that near-empty build directory, so the app tree is simply absent
  and the first build command fails with *"npm ci can only install with an
  existing package-lock.json"* — the 1.0.0 failure. Bump the `tag:` in the
  manifest's app-source block for every release; `npm test` fails if it does not
  match `package.json` and the newest metainfo `<release>`.
- **"Reference any companion source files by filename."** `generated-sources.json`
  therefore lives at the repo root, not under `flatpak/`.

Local builds and CI dispatch previews hid this: both run `flatpak-builder` inside
a full checkout, where `path: .` resolves to the real tree. CI now builds the
committed (git-source) manifest on **tag** builds, which is the only run that
exercises what FriendlyHub actually gets.

## Build artifacts (gitignored)

`build-dir/`, `.flatpak-repo/`, `flatpak-node/`, `*.flatpak`, and the generated
`chat.loft.Loft.dev.yml` are gitignored (repo-root `.gitignore`). Only the
manifest, `generated-sources.json`, the launcher, the dev-manifest generator, and
this README are committed.
